# Evaluation

How PharmaWatch AI is evaluated, what the stored results say, and what they do **not** say.

> **Read this first.** The dataset labels are **drafts written by an AI assistant**, pending
> validation by a vigilance specialist. The thresholds are **proposed**, not validated. The
> results below measure agreement with those draft labels on a held-out split; they are not a
> clinical or regulatory validation.

## Dataset: `golden_dataset_v2.json` (version 2.0.0)

| Property | Value |
|---|---|
| Cases | 152 (64 RAG questions, 88 incident classifications) |
| Languages | 105 English, 47 Spanish |
| Splits | `dev` 65 cases (27 RAG, 38 classification), `test` 87 cases (37 RAG, 50 classification) |
| Label source | `draft-ai` for every case: written from `data/regulations/` and `data/classification_rules.json`, not reviewed by an expert yet |
| Excluded from metrics | 6 borderline cases flagged `needs_expert_review` (3 in `dev`, 3 in `test`); see [open_questions.md](open_questions.md) |
| Coverage | at least 10 cases per deadline trigger, abstention (question not answerable from the corpus), prompt injection, false premises, noisy input, incidents with no device class hint |

The `test` split is frozen and must not be used to tune prompts; `dev` is for development.
`tests/test_dataset_v2.py` enforces the dataset invariants (ids, splits, label fields, no answer
leaked in the question).

The v1 dataset (`data/golden_dataset.json`, 30 cases) is kept for reference but is no longer
reported: its metrics were not comparable (see [CHANGELOG.md](CHANGELOG.md)).

## Protocol

| Setting | Value |
|---|---|
| Split | `test` — 84 cases scored (37 RAG + 47 classification; the 3 `needs_expert_review` test cases are excluded) |
| Repetitions | 3 (every case runs 3 times; metrics are reported as mean and min–max across repetitions) |
| System model | `claude-sonnet-5-5` |
| Judge model | `claude-sonnet-5-5` (faithfulness only) |
| Reviewer node | disabled (`REVIEWER_ENABLED=false`) |
| Code version | commit `938b456` |
| Run date | 2026-10-27 (UTC) |
| Model calls | system 439 calls; judge 111 calls |
| Re-scoring | the stored run was re-scored offline (no model calls) with the current metric code by `scripts/rescore_evaluation.py` |

A case **passes** only if it passes in all 3 repetitions; a case that passes in some but not all
repetitions is **flaky**.

The result file is `artifacts/evaluations/eval_v2_20261027T214319Z_rescored.json` (artifacts are
not versioned). Its summary — metadata, per-metric mean/min/max and thresholds, failed cases —
is versioned in [`docs/results/evaluation_latest.json`](results/evaluation_latest.json)
(generated by `scripts/export_eval_fixture.py`). That snapshot is what `scripts/check_docs.py`
checks the documentation against, what mock mode shows, and what `GET /evaluations/latest`
serves — labelled `"source": "snapshot"` — when an installation has no results of its own in
`ARTIFACTS_DIR`.

## Metric definitions

Rates are fractions of the cases where the metric applies; `n/a` means no case applied.

### Retrieval and answers (RAG, 37 cases)

| Metric | Definition |
|---|---|
| `retrieval_accuracy` | Expected source document among the 5 retrieved fragments. |
| `section_retrieval_accuracy` | Expected section (exact label, e.g. "Article 87") among the retrieved fragments. |
| `answer_accuracy` | Answer contains every required fact and nothing forbidden; for unanswerable questions, a correct abstention. |
| `abstention_accuracy` | Unanswerable questions where the system abstained. |
| `false_abstention_rate` | Answerable questions where the system abstained anyway. |
| `source_citation_rate` | Answerable questions whose answer cites at least one `[Cn]` label, and every cited label exists in the retrieved context. |
| `answer_faithfulness` | Judge model: share of the answer's claims supported by the retrieved context (strict prompt, full context), averaged over answers. |
| `hallucination_rate` | Answerable questions whose answer has at least one claim the judge finds unsupported, or a number not present in the context. |
| `numeric_grounding_rate` | Deterministic check over all answers: share of day counts, Article and Rule numbers that appear in the retrieved context. |

### Classification and deadlines (47 cases)

Accuracy metrics are computed over the cases whose label says the system should decide (not
escalate). They are end-to-end: a case the system blocks counts as not delivering the right
answer.

| Metric | Definition |
|---|---|
| `classification_accuracy` | Severity (serious / non-serious) matches the label. |
| `category_accuracy` | Incident category (death, unanticipated serious deterioration, public health threat, other serious, non-serious) matches. |
| `reportability_accuracy` | Reportable yes/no matches (a blocking escalation withholds the decision and counts as a miss). |
| `deadline_accuracy` | Deadline in days matches, over reportable cases; blocked cases count as misses. |
| `recipients_accuracy` | Recipient list matches, over reportable cases; blocked cases count as misses. |
| `deadline_accuracy_decided` | Deadline accuracy over the cases where the system did decide (not blocked). |
| `recipients_accuracy_decided` | Recipient accuracy over the cases where the system did decide. |
| `provenance_accuracy` | Device class and its source (`caller` / `extracted` / `rule`) both match the label. |

### Escalation and safety

Here **escalated** means a **blocking** escalation (the determination is withheld). Advisory
escalations keep the determination and are not counted as escalations by these metrics.

| Metric | Definition |
|---|---|
| `unescalated_error_rate` | Cases where a wrong determination reached the user without a blocking escalation (including a determination delivered where a human should have decided). |
| `dangerous_unescalated_error_rate` | Unescalated errors that under-report: a reportable incident delivered as not reportable, or a deadline longer than the one due. |
| `decision_rate` | Among cases the labels say are decidable, the share the system decided (not blocked). |
| `escalation_rate` | Share of all classification cases blocked. |
| `escalation_precision` | Blocked cases that the labels say needed a human. |
| `escalation_recall` | Cases that needed a human and were blocked. |
| `over_escalation_rate` | Among cases the labels say are decidable, the share blocked (1 − `decision_rate`). |
| `review_agreement_rate` | Reviewer node agreed with the principal decision (only when the reviewer is enabled). |

Latency metrics (`*_latency_p50_ms`, `*_latency_p95_ms`) are per request type, measured in the
harness on a developer machine; their thresholds are informative, not gating.

## Reading the weak metrics

**The system errs towards asking a human.** Every determination it issued without escalating
was correct (`unescalated_error_rate` 0 %, `dangerous_unescalated_error_rate` 0 %) and every
case that needed a human was escalated (`escalation_recall` 100 %). The price is
over-escalation:

- `deadline_accuracy` and `recipients_accuracy` (56.8 %) and `reportability_accuracy`
  (66.7 %) count a blocking escalation as a miss, because the system withholds the
  determination. Restricted to the cases where it did decide, deadline and recipients are
  100 % correct (`deadline_accuracy_decided`, `recipients_accuracy_decided`). The gap comes
  from blocking decidable cases (`decision_rate` 66.7 %), not from wrong deadlines.
- `over_escalation_rate` 33.3 % and `escalation_precision` 44.9 %: about a third of the cases
  that the labels consider decidable were blocked, and fewer than half of the blocked cases
  needed a human according to the labels. A review of the stored outputs points to
  category doubt between incident types with different obligations (by design, doubt
  escalates), low model-reported confidence, an unknown patient outcome, keyword signals that
  fire on benign wording, and missing device names. Proposed changes are listed in
  [open_questions.md](open_questions.md); none has been applied or measured.
- `source_citation_rate` 93.8 % (threshold 95 %): 2 of the 32 answers that should cite did not
  include a valid `[Cn]` label in every repetition.

Failed and flaky cases (ids and reasons) are listed in the result file and in the
**Evaluation** screen.

## Limitations

- **Draft labels.** The expected answers were written by an AI assistant from the same corpus
  the system retrieves from; agreement with them is not agreement with a vigilance specialist.
- **Proposed thresholds.** `config/eval_thresholds.json` reflects a reasonable starting point,
  not a validated acceptance criterion.
- **Same-family judge.** Faithfulness is judged by the same model family as the system. The
  deterministic numeric check reduces, but does not remove, that bias.
- **Small, synthetic test set.** 84 scored cases; synthetic narratives, not real incident
  reports. Min–max across 3 repetitions shows run-to-run variance, not a confidence interval.
- **Corpus scope.** Only MDR Articles 2(64)–(69), 87–89 and 92, Annex VIII and the AEMPS
  vigilance guidance are indexed. MDCG guidance documents are not in the corpus.
- **Reviewer ablation not run.** The optional reviewer node exists and is unit-tested, but its
  effect has not been measured (the evaluation account ran out of credit). No result is
  claimed for it.
- **Latency** was measured on one developer machine with 4 workers; it is not a service-level
  figure.

## Reproducing

Running the evaluation calls the model and **costs money** (the stored run made 550 model
calls). It needs `ANTHROPIC_API_KEY` and an ingested vector store:

```bash
python scripts/ingest_documents.py
python scripts/run_evaluation.py --dataset v2 --split test --repetitions 3
python scripts/check_eval_thresholds.py
```

Re-scoring a stored result with the current metric code is free (no model calls):

```bash
python scripts/rescore_evaluation.py artifacts/evaluations/<result>.json
python scripts/export_eval_fixture.py
python scripts/check_docs.py
```
